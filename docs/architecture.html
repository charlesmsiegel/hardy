Hardy — the complete design map

an agentic harness for theorem proving · Lean 4 + LaTeX · any model · every decision to date

Claude Code and Codex proved that the harness around a model — the loop, the tools, the feedback channels, the context management — matters as much as the model itself. Hardy applies that lesson to formal mathematics, where the payoff is uniquely large: verification is free and perfect. Code has incomplete tests and prose has subjective quality, but the Lean kernel gives an unambiguous ground-truth verdict on every attempt. Hardy's job is to keep any capable LLM in a tight loop with that signal.

IN → OUT The output contract LaTeX always · Lean where possible

“Prove that √2 is irrational.”

TeX sqrt2_irrational.tex
formal statement · informal proof · citations · compile-checked · always produced
∎ Sqrt2Irrational.lean
kernel-checked proof of the same statement · whenever formalization is in reach

The two artifacts are cross-linked; the LaTeX records formalization status. A LaTeX proof marked “not yet formalized” is a result — a failed Lean attempt alone is not. This mirrors how draft-sketch-prove systems work: informal reasoning first, formal second.

NAME Why “Hardy”

In 1913, G.H. Hardy received a letter from Srinivasa Ramanujan: pages of extraordinary claims, stated without proof. Hardy's response defined the collaboration — recognize the brilliance, then demand the proof. That is precisely this harness's relationship to the model plugged into it: the LLM supplies the flashes of insight; Hardy supplies the rigor, the verification, and the insistence that nothing ships until it's proved.

Hardy also wrote A Mathematician's Apology — the writeup matters as much as the proof, which is why every result here comes with one.

Every proof-oriented request is one of three composable workflows, or a chain of them. They hand a single problem back and forth — Prove drafts, Critique finds the gaps, Repair closes them one at a time, Critique re-checks — around the loop until no hole remains open or the remaining ones are honestly reported. (A fourth workflow, Assume — “assume this paper” — prepares axiomatized paper libraries, standalone or as a preparatory step; see Frontier Math.)

W1 Prove

“Find a proof of X.” Formalize the statement (with a faithfulness check that the Lean statement matches the informal claim), search for a proof using the strategy stack, and produce the LaTeX + Lean artifact pair.

W2 Critique

“Find holes in this proof.” Takes any proof — user-supplied, from the literature, or Hardy's own draft — and produces a structured hole ledger: unjustified steps, missing cases, quantifier slips, circular arguments, misapplied citations.

W3 Repair

“This proof has a hole; propose a fix.” Takes one ledger entry and patches it locally — a bridging lemma, an added case, a corrected calculation — without regenerating the whole proof. Every patch is verified: kernel where formal, re-critique where informal. A repair may change the proof, never the claim — a fix that would strengthen a hypothesis or weaken the conclusion is reported as a revised claim, a distinct outcome, never a successful repair of the original.

DETECT Three detection layers strongest first

  • Kernel — for Lean-backed proofs, holes are free and exact: sorrys, failed elaboration, axiom-manifest surprises.
  • Formalization probing — for informal proofs, attempt to formalize each step; a step that resists formalization is a suspected hole. This is the deep reason the dual-output contract pays off: formalization is hole detection.
  • Adversarial skeptics — agents prompted to break each step: seek counterexamples to intermediate claims, check edge cases, verify cited results actually say what the proof needs.

Nine components, from the REPL plumbing at the bottom to telemetry at the top. The tool layer is the heart of the harness thesis: tool design carries the Lean expertise, so even weaker general-purpose models can function.

C1 Lean interaction layer the foundation everything sits on

Whole-file lake build cycles take 30 s–minutes with Mathlib — far too slow for an inner loop. The model needs fast, structured feedback:

Persistent REPL sessions
Mathlib imported once, reused across many attempts. Start with leanprover-community/repl (JSON-over-stdio, proof-state pickling); keep the layer abstract enough to swap in Pantograph or LeanDojo.
Structured feedback
Goal states (hypotheses + targets), errors with positions, warnings, elaboration info — parsed into typed objects, never raw text.
Two checking granularities
Tactic-level: one tactic against a proof state, enabling tree search. Declaration-level: the whole proof — the final source of truth.
Incremental via sorry
Sketch a skeleton with have/sorry placeholders, discharge each subgoal independently — parallelizes naturally.
State pickling
Snapshot and restore proof states so search can branch without replaying tactic prefixes. Pickling restores proof states, not declarations — so independent runs fork from the pristine pinned environment (warm process, clean declarations) to prevent cross-run contamination.
Resource limits
Per-tactic and per-proof timeouts (maxHeartbeats, wall clock, memory) — a runaway decide or simp must never stall the loop.

Design rules learned from coding agents: tools return compact, high-signal output (truncate huge goal states, dedup repeated errors) · errors are actionable (failing position, expected vs. actual type, nearby context) · the model never guesses hidden state — everything is observable via tools.

C3 Agent runtime layer "plug any model in", realized one level above completions

Hardy abstracts over agent runtimes — systems that own the model loop and tool execution. All 16 tools are defined once (name, JSON schema, handler) in harness code; each adapter only exposes them to its loop. That seam keeps the Lean/LaTeX/arXiv logic free of any SDK dependency. The interface is roughly run(task, tools, config) → Trajectory.

Claude Agent SDK first
Production-quality loop, native tool use, context compaction, subagents for free. The MVP builds here.
Strands Agents second
The proof the abstraction holds — and multi-provider model support (Bedrock, LiteLLM, …) through one adapter.
Minimal built-in loop third
Ollama / vLLM / OpenAI-compatible endpoints. Native tool calling where supported; prompted-JSON fallback where not. This is what “any model” ultimately means.
  • Config, not code — runtime, model, context window, cost caps, parallelism, reasoning-effort knobs are all per-run configuration.
  • Prompt templates versioned and swappable — prompt strategy is a first-class experimental variable.
  • Leaky-abstraction policy — runtime-specific features (SDK subagents, compaction) live behind capability flags, but every strategy must have a degraded-but-functional path on the minimal loop so results stay comparable across runtimes.

C4 Orchestration & search strategies pluggable, benchmarked against each other

The Prove / Critique / Repair workflows (→ Workflows view) run on a strategy stack. A single agent in a loop is the baseline; the interesting work is layered on top:

1 · Iterative repair MVP
Attempt whole proof → read errors → revise → repeat within budget. Surprisingly strong with good error feedback.
2 · Sketch-and-discharge
Informal plan → have/sorry skeleton → subgoals discharged independently; parallel sub-agents, cheaper models on easy subgoals.
3 · Best-first tactic search
Frontier of proof states; the model proposes k tactics per state, ranked by model or heuristic scores. AlphaProof/ReProver-style with a general LLM as the policy.
4 · Parallel diverse attempts
n independent attempts, different temperatures/prompts/strategies; first verified proof wins. Verification makes majority voting unnecessary — pass@k is the natural metric.
5 · Hybrid automation
Cheap closers first — simp, omega, aesop, exact?, duper — before spending model tokens on a subgoal.
Cross-cutting
Budgets (tokens, wall-clock, Lean CPU; graceful degradation) · context management (failed attempts distilled into lessons, not replayed) · memory across theorems (later).

C5 Literature & writeup layer

  • arXiv integration — search with category/author/date filters; downloads prefer LaTeX source over PDF text (far more useful to a model); content-addressed store at papers/<arxiv-id>/; rate-limited, cached, never re-fetches.
  • Bibliography — one canonical machine-maintained references.bib: entries auto-generated from arXiv metadata, deduped by arXiv id/DOI, stable cite keys (author2023short), validated in CI. The cite tool is the only write path.
  • LaTeX pipeline — standard template with theorem/proof environments and a formalization-status block linking the .lean file; every document compile-checked (tectonic/latexmk) with errors fed back — the same loop shape as the kernel, weaker guarantee. Compilation is sandboxed like Lean elaboration: TeX is code (\input, \openout, shell-escape), so generated documents build with shell-escape off, no network, read-only mounts, and an ephemeral output dir.
  • Results layout — results/sqrt2_irrational/ holds .tex, .lean, and a manifest recording status and provenance.

C7 Environment management

  • Pinned toolchain — lean-toolchain + pinned Mathlib revision; lake exe cache get for prebuilt oleans. Reproducibility is non-negotiable for benchmarking.
  • Warm session pool — REPL workers cost 30–60 s to start (Mathlib import); keep a warm pool, recycle on memory bloat or crash. Between independent runs, workers reset to the pristine base environment — one run's declarations and axioms must never leak into the next.
  • Sandboxing — model-generated Lean can execute arbitrary IO at elaboration time (#eval, native_decide): workers run in containers with no network and a read-only filesystem plus an ephemeral scratch dir (per-invocation tmpfs with size/inode quotas, wiped on recycle — untrusted code can't fill host storage). The LaTeX compiler runs under the same regime — generated TeX is equally untrusted.
  • Docker image — toolchain + Mathlib cache baked in, for CI and reproduction.

C9 Telemetry & trajectories

  • Every run logged as a structured trajectory: messages, tool calls, Lean feedback, timings, token counts.
  • Uses: debugging the harness, comparing strategies, mining failure modes — and eventually distillation/fine-tuning data for smaller models.
C6 (assumed-paper libraries) has its own view — Frontier Math — and C8 (evaluation) lives in Trust & Eval. They're the two components with the most subtlety, so they get room to breathe.

Mathlib covers a lot, but real research builds on results that will never be formalized bottom-up in time to be useful. The escape hatch: “assume this paper” — formalize a paper's statements (never its proofs) as Lean axiom declarations, and prove new results in the context of those assumptions. This is how working mathematicians already treat the literature; Hardy just makes the trust chain machine-checked.

MECH The mechanism Lean's axiom is exactly the right primitive

Axiom dependencies are tracked by the kernel and surfaced by #print axioms, so a downstream theorem automatically reports which paper results it leaned on:

namespace Papers.Smith2023 -- arXiv 2301.12345 /-- Theorem 3.2 of [smith2023modular]: … -/ axiom modular_lifting (p : ℕ) (hp : p.Prime) (hp5 : 5 ≤ p) : … end Papers.Smith2023

The anti-cheat check stops being just a cheat detector and becomes a dependency ledger: every result is either fully verified (standard axioms only) or verified modulo an explicit list of assumed paper results.

HARD The hard part: definitions

A theorem statement can be axiomatized, but it usually refers to objects the paper defines — and definitions cannot be assumed the same way. In order of preference:

  • 1 · Map onto Mathlib when a matching definition exists — best, and makes the axioms interoperate with all of Mathlib.
  • 2 · Write a real Lean definition when it's cheap.
  • 3 · opaque constant + characterizing axioms — viable, but each characterizing axiom widens the trust surface.

RISK Soundness, managed not ignored

  • Inconsistency — a mis-formalized axiom can make False derivable, letting the agent “prove” anything. Mitigations: the faithfulness review; minimal libraries (only assume what's used); refutation lints (decide/simp counterexample hunting on decidable statements); the manifest making any bad axiom's blast radius knowable after the fact.
  • Definitional drift — the Lean rendering may subtly differ from the author's intent, so every writeup using assumed results states them in prose (“assuming Theorems 3.2 and 4.1 of [smith2023modular]”) — the trust chain stays auditable without reading Lean.
Adopted: eager inventory, lazy minting — the full statement inventory is extracted up front (browsable), but an axiom is minted and faithfulness-reviewed only when a proof first invokes that result, keeping the trusted surface minimal. Still open: chase transitive citations (paper A depends on paper B)? — take A at face value first; the manifest records exactly what was taken on faith either way.

You can't improve what you don't measure — and in a domain where the agent could look successful while cheating, measurement and honesty are the same system. Every result carries a grade; every “solve” is audited.

GRADE The trust ledger two orthogonal dimensions — every result carries one grade from each

Formalization status

Fully verified — kernel-checked with standard axioms only (propext, Classical.choice, Quot.sound)
Verified modulo — kernel-checked, plus an explicit list of assumed paper results from #print axioms
Partially formalized — Lean skeleton with sorrys remaining; the partial artifact is kept and its holes listed
Not formalized — no usable Lean artifact; formalization not yet attempted or out of reach

Informal completeness

Complete — the writeup's argument has no unresolved holes
Known gaps — critique–repair budget expired with holes abandoned; they're listed in the writeup, never hidden behind a clean grade
Not assessed — pre-M6 runs, before the hole ledger and critique loop exist; never defaulted to complete

The dimensions are independent, so every result has a deterministic verdict — a kernel-verified theorem with a gappy writeup is fully verified × known gaps; a clean informal proof with a sorry-laden skeleton is partially formalized × complete.

C8 Evaluation harness

  • Benchmarks — miniF2F (Lean 4 port) first; then PutnamBench, ProofNet (formalization), and a held-out custom set to catch contamination/overfitting.
  • Metrics — solve rate at fixed budget (pass@1, pass@k), cost per solved theorem (tokens + Lean CPU), wall-clock, per-domain breakdowns (algebra vs. number theory vs. analysis).
  • Output-contract check — outside benchmark mode a run isn't complete without its compile-checked writeup; the Lean artifact is graded verified / partial / absent.
  • Regression tracking — every prompt/tool/strategy change runs against a fixed eval set, logged with config hashes so runs are comparable.

AUDIT Anti-cheat validation on every claimed solve

  • Proof is sorry-free and compiles against the original, unmodified statement.
  • #print axioms shows only expected axioms — no sorryAx, no smuggled axioms. Benchmark runs allow zero paper axioms; frontier runs report the manifest with the result.
  • Suspicious closers flagged for review: native_decide, decide on huge goals.
Why so paranoid: a prover that can modify its statement, smuggle an axiom, or lean on an inconsistent assumption can “solve” anything. The audit is what makes the headline numbers mean something.

STACK Proposed stack

  • Harness — Python (model APIs, async orchestration, analysis); Lean side stays in Lean, JSON over stdio.
  • Agent runtimes — claude-agent-sdk → strands-agents → hand-rolled minimal loop.
  • Lean — leanprover-community/repl, Mathlib (pinned).
  • Literature/writeup — arxiv, bibtexparser, tectonic or latexmk.
  • Plumbing — pydantic for typed tool/trajectory schemas.

LATER Explicitly out of MVP scope

  • Autoformalization at scale — single-statement NL → Lean formalization is core from M1 (with a faithfulness check before proving); the deferred part is bulk corpus formalization and automated statement-equivalence checking.
  • Premise-retrieval model — embedding-based Mathlib retrieval (ReProver-style).
  • Lemma library growth — the agent proposes and proves reusable intermediate lemmas.
  • Multi-agent review — a skeptic that inspects statements for vacuity or mis-formalization before effort is spent.

OPEN Open questions with current leanings

  • REPL choice — leanprover-community/repl vs. Pantograph vs. LeanDojo. Prototype against repl; keep the layer swappable.
  • Statement source of truth — benchmarks provide statements; for general use the agent formalizes, with a faithfulness check. Bulk autoformalization deferred.
  • How much Lean-specific prompting is too much? — the harness goal is that tool design carries the Lean expertise, so weaker general models still function.
