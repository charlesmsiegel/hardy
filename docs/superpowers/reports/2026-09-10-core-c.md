## Environment and limits

Baseline: 187 existing seam/boundary tests passed before implementation. Tests
use the isolated worktree's Python 3.13.11 environment; no project dependencies
were added. Installed-wheel verification uses a fresh environment and resolves
the distribution's declared dependency ranges.

The first unfiltered invocation discovered the machine's configured Lean project
and entered `test_every_canonical_statement_elaborates`, a whole-corpus real
sweep. It was explicitly stopped, with no pass result claimed. The complete
hermetic gate uses the repository's `real_toolchain`/`live` marker separation;
CI's hermetic job normally has no installed project and skips those probes.
The initial log remains `%TEMP%/hardy-core-c-hermetic.log`. No corpus sweep
artifacts were relabelled as test evidence.

The fresh checkout has no ignored local evaluation baseline or scoreboards.
Their existing absence-based skip rules apply; stale artifacts in the main
workspace were neither copied, relabelled nor removed. The actual corpus content
is unchanged. Source changes invalidate old run-procedure identities normally.

Acquisition composes named model/search/materialization/admission operations;
production project-workflow adapters and user-facing Research/Explore integration
remain Core D. B4/B5 semantic operations can be registered at the C4 boundary;
there is no domain parser or automatic semantic choice hidden in scheduling.

Sketches are explicit independent local-lemma decompositions, not arbitrary Lean
metavariable extraction. Each attempt requires a fresh run store. Callers retain
authenticated scope, independent hole-provider contexts, runtime tool ceilings
and cancellation of work already in flight. No new sandbox, shared CPU pool,
token/cost reserve-settle system or benchmark improvement is claimed.

## Design retained

The ledger records history; capability owners supply authority. Acquisition
turns missing work into exact proposals and explicit children, and never makes
an assumption true by changing its category. The recursive resolver reuses B0
transactions and B1/B2 graph/policy queries rather than maintaining another
database. Attempt/depth limits bound scheduling; external operations retain their
own timeouts. Strategies propose proofs under run-owned ceilings; only a fresh
check of the assembled original claim can establish the final result.
