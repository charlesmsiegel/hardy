What Hardy is

Hardy is an agentic harness for proving theorems in Lean 4, built on one architectural conviction: the harness — never the model — owns verification, budgets, artifacts, and the distinction between a promising argument and a checked proof. A model proposes; Lean's kernel decides; Hardy records what was actually established and under which assumptions.

Its shape is a CLI-driven layered monolith: a thin argparse front door over a flat core package, with two model backends behind one protocol, and subprocess adapters for the three external authorities it cannot fake — Lean, LaTeX, and a computer algebra kernel. There is no network daemon, no HTTP service and no database — durability is files on disk (JSON manifests, JSONL trajectories, a Lean workspace tree). There is one server in the process sense: src/hardy/mcp_server.py:31 builds a FastMCP instance and runs it over stdio (src/hardy/mcp_server.py:279) so clients other than the in-process agent SDK — the Codex backend among them — can reach the same bounded Lean and CAS tools.

The dominant design tension, stated repeatedly in the code's own comments: Hardy authenticates through Claude Code's agent SDK to run on a subscription rather than a metered key, and the price of that is the agent loop itself — the SDK decides when a model call happens. What Hardy refuses to surrender is the trust boundary (src/hardy/claude_runtime.py:9-14).

Key decisions & constraints

Subscription auth, at the cost of the loop

The Claude backend drives the Claude Code CLI through claude-agent-sdk, so a Max subscription works with no API key. The SDK therefore owns turn scheduling. The costs are recorded rather than glossed: turn limits become the SDK's to enforce, cheap Lean closers cannot run before a model turn is spent, and token budgets have no decision point. Hardy therefore built its own wall clock, because nothing in the SDK bounds a stalled request (src/hardy/claude_runtime.py:322-331) — but staged prove never passes a value to it, so on the flagship path that guard sits inert. See Invariants & Risks.

Default-deny tool permissions Claude only

can_use_tool refuses anything not prefixed mcp__hardy__ (src/hardy/claude_runtime.py:211-220). The REFUSED list at src/hardy/claude_runtime.py:64 is explicitly belt-and-braces; the comment explains that a denylist has to anticipate every built-in the CLI might grow, and this cannot. setting_sources=[] also refuses to inherit the user's own CLAUDE.md — "a run that silently inherits them is not the run its record claims."

The Codex backend does not have this. CodexRuntime.start relies on the Codex SDK's own workspace_write sandbox and auto_review approval mode (src/hardy/codex_runtime.py:100-101) and registers Hardy's tools over stdio MCP, with no permission callback and no denylist — so under --backend codex the model is not restricted to Hardy's registered verbs. Both runtimes keep the part that matters most (Hardy still performs every Lean check itself), but they are not the same boundary.

No sandbox, said out loud

The reset deliberately removed the old container sandbox. Rather than scan CAS cell source for os.system — trivially bypassable while implying safety that does not exist — the warning is stated in prose wherever a human is looking: the chat banner, the staged run's typed acknowledgement (src/hardy/workflow.py:141-150), the MCP tool descriptions, and the header comment of every exported script (src/hardy/cas_export.py:341). This is the single largest accepted risk in the project.

One executable surface does not show it. The exported .ipynb carries WARNING only in metadata.hardy.warning (src/hardy/cas_export.py:420), and render_notebook emits cell_type: "code" for every record and no markdown cell at all (src/hardy/cas_export.py:379-415) — so a reader who opens the notebook in Jupyter and runs it sees the recorded cells and none of the warning, since no normal notebook view renders that metadata key. The sibling script warns and the notebook does not, which is the wrong way round: the notebook is the artifact people actually re-run. A leading markdown cell would fix it in one line.

Threads, not async, at the seams

The SDK is async and no caller is. A turn runs on a daemon worker thread with events crossing back through a queue.Queue (src/hardy/claude_runtime.py:225-265), and tool dispatch hops off the event loop via asyncio.to_thread because tools run subprocesses and one of them stops to ask a human (src/hardy/claude_runtime.py:127-131). The CAS kernel serialises everything under one lock.

Frozen values, canonical hashes

The values that must not drift are FrozenModel subclasses — extra="forbid", frozen=True (src/hardy/domain.py:20-23) — covering FrozenClaim, Grades, RunLimits, EnvironmentIdentity and the CAS records. Claim identity is a SHA-256 over canonically-serialized JSON (src/hardy/domain.py:80-97), and the prompt set gets the same treatment.

Two exceptions worth knowing, both of them central persisted artifacts. RunManifest — the result of a prove run — is a plain BaseModel with extra="forbid" and no frozen=True (src/hardy/domain.py:168-169), so its fields and its artifacts/timings_ms/usage dicts stay mutable after validation; the workflow assembles it incrementally, which is why. And the interactive session's session.json file is read and written as a plain dict with no schema validation at all (src/hardy/chat.py:289-297) — a schema_version key is set by hand on first creation and never checked — as is that session's transcript, which _record appends as bare JSON objects stamped with a wall-clock float (src/hardy/chat.py:319-322). So frozen=True and extra="forbid" are properties of the claim, the grades and the CAS records, not of everything Hardy writes down.

The staged trajectory is not in that company, and the two event streams should not be read as one. RunStore.append constructs a TrajectoryEvent — itself a FrozenModel (src/hardy/storage.py:37-44) — and serialises it through model_dump_json, and RunStore.open re-validates every line on read and then checks that each event's run_id matches and that its sequence equals its position, raising rather than continuing if either fails (src/hardy/storage.py:89-95). A staged trajectory is therefore a schema-checked, gap-free, per-run-verified log; the interactive transcript is an append-only file of whatever dict the caller passed.

Two backends, one protocol

Claude (src/hardy/claude_runtime.py) is required; Codex (src/hardy/codex_runtime.py, 200 lines) is an optional extra for ChatGPT-subscription users. Both satisfy the same narrow runtime shape, and hardy prove --backend selects between them (src/hardy/cli.py:620).

Evaluation artifacts

Acceptance problems exist; results do not. The repo ships a checked-in problem set (src/hardy/acceptance_problems.json, mirrored at acceptance/problems.json) and a runner (src/hardy/acceptance.py, src/hardy/cli.py:528), with a consistency test tying the two manifests together (tests/integration/test_manifest_consistency.py:34). There are no recorded results in the tree — consistent with DESIGN.md's own admission that "a real model/Mathlib acceptance run remains to be recorded." The scaffolding for honest evaluation is built and unused; that is a milestone, not a defect, but it means no claim in this repo about end-to-end proving has been demonstrated.
The diagrams need network access on first load. This file is self-contained in every respect but one: the renderer for the five Mermaid diagrams (Overview and Critical Flows) is fetched from cdn.jsdelivr.net at runtime. Opened offline, or behind a policy that blocks jsDelivr, those diagrams show their raw Mermaid source instead. That degradation is deliberate rather than accidental: this file's own Mermaid loader registers an s.onerror handler that restyles every .mermaid block as monospaced, horizontally scrollable preformatted text, and its onload path repeats the same fallback if the script arrives but mermaid is undefined. So the diagram sources stay legible as indented graph definitions rather than reflowing into a wall of prose — what is lost offline is the rendered picture, not the content. Every other tab, including all tables and both interactive graphs, works with no network at all. This is a limitation of the generator's template, not of this repository.

Four flows where correctness actually matters: the staged prove pipeline, the interactive Lean save, the CAS state rebuild, and turn cancellation. Each diagram shows the unhappy paths, because that is where this codebase spends its care.

Seams

The claim hash is re-checked twice, on both sides of persistence. Once when the approved claim is read back (src/hardy/workflow.py:277-284, raising RuntimeError on mismatch) and again inside the verifier (src/hardy/verifier.py:82-99, returning STATEMENT_MISMATCH). Belt-and-braces on the one thing that must not drift; note the two responses differ — an exception versus a graded failure.
Seven exits, ten hand-threaded arguments. run() is 311 lines (src/hardy/workflow.py:128-438) and every exit calls _finalize with the same ten values — request, terminal, store, state, created_at, active_started, user_wait, grades, reason, claim (src/hardy/workflow.py:439-451, seven call sites). active_started and user_wait in particular are a hand-rolled stopwatch: every exit must subtract user wait from active elapsed correctly, and nothing structurally prevents a future eighth exit from getting it wrong.
Three different ways to leave formalization without a claim, and the reason is preserved. A user choosing cancel finalizes immediately as USER_REJECTION (src/hardy/workflow.py:248-260). An expired active budget sets TIMEOUT_BUDGET_EXHAUSTED and breaks (src/hardy/workflow.py:206-209). Only a genuinely exhausted proposal budget falls through to MALFORMED_MODEL_OUTPUT, and the terminal_reason or … at src/hardy/workflow.py:287-292 is what keeps an earlier reason from being overwritten. Worth reading before trusting a persisted terminal reason: the distinction is real and easy to flatten.
Budget checks happen at loop tops, not during work. Both loops test elapsed time before starting an attempt (src/hardy/workflow.py:200-204, :311-320). A single proof attempt that overruns cannot be interrupted by the active_seconds budget — only by the per-process Lean timeout. A run can therefore exceed active_seconds by up to one attempt's duration, and the recorded timing will say so honestly, but the budget is a floor on granularity rather than a ceiling on wall time.
Cancellation is caught, not leaked. KeyboardInterrupt and any Exception both land in _finalize with a proper terminal reason (src/hardy/workflow.py:388-424), and active_thread is deliberately assigned as early as the formalizing phase so a Ctrl+C during formalization still reaches the runtime's cancel — the comment at src/hardy/workflow.py:196-200 explains that without it the provider thread could still be appending while _finalize hashes the run directory.

Seams

Every refusal is atomic. The save is staged into a shadow workspace and only committed after the whole affected module set builds (src/hardy/chat.py:461-486, src/hardy/workspace.py:455-513), with discard in a finally. "Nothing was written" appears in three separate refusal messages and is true in each.
This gate is not the verifier's gate. _final_gates (src/hardy/chat.py:324-340) checks sorry/admit via src/hardy/lean.py:28 and matches declared axioms against the approved set. It never runs #print axioms. So a theorem saved through the interactive workspace has no recorded axiom dependency set, while one graded by prove does. Detailed on the Invariants tab.
The pre-check was removed on purpose, and the comment says why. _save_lean skips a standalone elaboration because the shadow build elaborates the file anyway, and with Mathlib imported each elaboration costs tens of seconds (src/hardy/chat.py:455-461). The consequence is that Lean's own diagnostics have to be captured out of the build callback into a seen dict, and a byte-identical source that the cache skips returns the string "unchanged; already built" instead of compiler output (src/hardy/chat.py:487-489).

Seams

A rebuild that reconstructs different values poisons the session rather than reporting success. _restore replays only accepted cells and compares each against its record; divergence sets state = "poisoned" and raises (src/hardy/cas.py:1338-1350). The comment names the exact hazard: a cell depending on randomness, time, or the filesystem can succeed on replay and still reconstruct a different value.
Replay is billed, and a reset does not refund. Rebuild time is charged to spent_seconds (src/hardy/cas.py:1329) and _guard() runs a second time afterwards, so the rebuild can be what exhausts the budget. reset deliberately does not refund, because cas_reset is a model-callable tool and refunding would make the session budget advisory (src/hardy/cas.py:1352-1366).
A truncated sentinel cell mutates live state that replay will never reproduce. When a Singular or Macaulay2 cell exceeds cas_output_bytes, its status was classified from a prefix and an error banner may sit in the discarded tail, so the cell is recorded but excluded from accepted (src/hardy/cas.py:1265-1281). It did change the namespace. The session therefore knowingly holds live state outside its own replayable set, and the model is told so in a 7-line note. This is handled about as honestly as it can be without re-running the cell — but it means "the live kernel and the accepted log agree" is not an invariant this code can promise.
Export asks two questions and requires both. Replaying cells and running the published file are different claims — a kernel evaluates a trailing expression where a script discards it — so export compares both transcripts and reproduces only when both hold (src/hardy/cas_export.py:81-87). A prefix-truncated capture can only yield unverified, never verified (src/hardy/cas_export.py:113-122).

sequenceDiagram

Seams

stream is deliberately not a generator. A generator body does not run until first iterated, and iteration happens on a worker thread — so the per-turn reset of _cancelled would land after an Esc pressed in the same input batch as the Enter that started the turn, wiping the cancellation while the terminal and transcript both claimed the turn had stopped (src/hardy/claude_runtime.py:227-238). Subtle, correctly reasoned, and exactly the kind of thing that regresses silently.
Cancel crosses threads with no lock. cancel() is documented as safe from any thread and reads _loop/_client via a snapshot (src/hardy/claude_runtime.py:283-295), suppressing RuntimeError because the loop can stop between the check and the call. Correct in CPython by attribute-read atomicity, but it is a convention held by comment. tests/test_cancel_races.py exercises the paths; a race this shape cannot be proven absent by testing.
A consumer that stops early must not orphan the producer. _consume's finally calls cancel() whenever the stream was not drained to _FINISHED, then joins with a timeout (src/hardy/claude_runtime.py:265-281). The thread is a daemon, so the join bounds tidiness rather than safety — and settle() exists precisely so a caller about to write down what a run produced can learn whether the thread actually finished (src/hardy/claude_runtime.py:297-311).

The boundaries that matter are held; the plumbing is duplicated

Hardy's security and verification boundaries are unusually clean for a project this young — with one caveat that is backend-shaped. What a model may call has a single Hardy-owned decision point on the Claude backend only; under --backend codex there is no Hardy-side gate at all, and the boundary is the Codex SDK's own workspace_write sandbox and auto_review approval mode. What counts as verified has one owner, and one file owns the CAS kernel protocol. The smearing is in ordinary infrastructure — durable writes, output bounding, and the hole/axiom checks that exist twice with different strictness.

Boundary violations & cycle semantics

One design-meaningful back edge, inside a five-file strongly-connected group. The Dependencies tab lists that group as src/hardy/cli.py, src/hardy/tui/__init__.py, src/hardy/tui/plain.py, src/hardy/tui/shell.py and src/hardy/tui/stream.py — an alphabetically sorted set of members, not a path, so it should not be read as a chain of imports. Only one edge in it is a design decision.
  • The real one. src/hardy/tui/__init__.py imports cli inside two functions (src/hardy/tui/__init__.py:31, :46) while src/hardy/cli.py imports tui.ports at module level (src/hardy/cli.py:24) and tui itself inside a function (src/hardy/cli.py:86). The reason is documented at src/hardy/tui/__init__.py:20-26: the shell must exist before the session does, because the session needs an axiom-approval callback and that callback runs through whichever Ui ends up live.
  • The other three are ordinary Python. src/hardy/tui/plain.py, src/hardy/tui/shell.py and src/hardy/tui/stream.py each say from . import … (src/hardy/tui/plain.py:13, src/hardy/tui/shell.py:51, src/hardy/tui/stream.py:20), which counts as an edge to the package initializer — and the initializer imports plain and shell back. A package importing its own submodules is not a design problem. There is no src/hardy/tui/stream.py → src/hardy/cli.py edge at all: stream.py imports only transcript.

The fix for the one that matters is small and structural: confirm_assumption (src/hardy/cli.py:27-60) depends only on the Ui port and Choice, not on anything else in cli. Moving it into tui/ — next to src/hardy/tui/ports.py, where its only dependency lives — removes the back edge and the need for deferred imports. That the current arrangement is deliberate and commented makes it a design debt rather than a bug, but a lazy import is a cycle you have agreed to stop noticing.

The reported src/hardy ↔ prompts ↔ tui module cycle is the flat-package artifact. With 30 files in one directory, "module" and "package" coincide, so any subpackage importing back into the core (prompts imports ..domain; tui imports ..cli) reads as a cycle at module granularity. Only the tui ↔ cli half is a real one; prompts → domain is a leaf importing a leaf.
src/hardy/cli.py is the intended dependency sink, and it is filling up. Fan-out 26 — the highest in the repo, ahead of the CI workflow file. Failure handling

The broad excepts are deliberate, and the ones on the interactive surface fail in the safe direction. There are ten except Exception handlers in src/hardy/, not the three an earlier draft of this callout claimed. Eight carry a noqa and a stated reason, and the reason is nearly always the same one: never lose the session to one bad turn. The axiom gate returns False on any exception (src/hardy/cli.py:55); run_session falls back to the plain UI (src/hardy/tui/__init__.py:40); the plain loop and the shell each catch around session.stream and around command dispatch, print the error and continue (src/hardy/tui/plain.py:147, :188, src/hardy/tui/shell.py:516, :647, :712). Those five report to the user before continuing, so nothing is hidden — but they do convert a failed turn into a continued session, which is a policy choice worth knowing rather than an invisible one.

Two are worth separating out. src/hardy/cas_export.py:482 converts a failure of the script check into the verdict unverified naming the error, on the documented grounds that a partial export must be written and marked rather than withheld — it degrades the claim instead of losing the artifact, which is the right trade and is argued for in the comment. src/hardy/workflow.py:417 and src/hardy/runner.py:99 are the two with no noqa and no reason: the workflow one records workflow.error in the trajectory and then finalizes the run as AGENT_RUNTIME_FAILURE regardless of what actually failed, so a persistence, verification or writeup fault is filed against the model runtime. That is the misattribution described on the Invariants tab, and it is the one handler here that loses information a reader of the manifest needed.

The doctor health gate reads a possibly-absent attribute with a permissive default. getattr(report, "authenticated", True) is False (src/hardy/workflow.py:175-179) — a report object that has lost the attribute is treated as authenticated, and the run is recorded as SETUP_FAILURE rather than AUTHENTICATION_FAILURE. Only the terminal reason is affected, not whether the run proceeds; still, a getattr default is a type hole where a protocol would do.
Timeouts exist everywhere except the one place the project says it covers. Lean (lean_process_seconds), TeX (tex_process_seconds), CAS cells and CAS sessions all have process bounds in RunLimits (src/hardy/domain.py:26-42). For the model call, which the SDK's loop owns, Hardy built its own wall clock — _within_budget wraps the exchange in asyncio.wait_for and records that Hardy enforced the stop (src/hardy/claude_runtime.py:322-331). On staged prove that code never runs: wall_seconds is left None at construction (src/hardy/staged.py:145-152), so the guard takes its unbounded branch, and run() only tests the budget between attempts (src/hardy/workflow.py:311-320). A provider request that hangs holds the run open indefinitely. The batch path, which does pass a bound (src/hardy/runner.py:85), even records "wall_clock_enforced_by": "hardy" in its trajectory — the claim is true there and only there.
Every harness failure is filed against the model runtime. run() classifies KeyboardInterrupt specifically, then labels everything else AGENT_RUNTIME_FAILURE (src/hardy/workflow.py:405-424) — including failures in persistence, claim reloading, Lean setup, verification and writeup construction, none of which are the runtime's fault. TerminalReason.INTERNAL_ERROR exists for exactly this and is referenced nowhere outside its own declaration (src/hardy/domain.py:125). It is one of two dead members: PROOF_INCOMPLETE (src/hardy/domain.py:117) is also never produced, appearing only in a serialization test (tests/unit/test_storage.py:100) — so 12 of the 14 declared reasons can actually reach a manifest. For a project whose purpose is honest experiment records, a terminal reason that misattributes blame is a data-quality bug, not a cosmetic one.
Secret redaction is key-name based. storage._redact (src/hardy/storage.py:159-170) replaces values whose key matches a secret pattern, recursing through dicts and lists. A credential appearing inside a free-text value — a model message, a Lean error, a subprocess stderr — is not caught, and trajectories record all three. Reasonable for a local-first tool; worth knowing before any run directory is shared.

Concurrency

Three distinct models coexist, and the boundaries between them are where this codebase is most intricate.

Turn worker thread

The SDK's event loop runs on a daemon thread; events cross to the caller via queue.Queue. _cancelled, _loop and _client are written by the submitting thread and read by cancel() from any thread with no lock, using a snapshot and a suppressed RuntimeError (src/hardy/claude_runtime.py:283-295). Sound under CPython attribute atomicity; a convention held by comment, not by a primitive.

Tool dispatch hop

Tools leave the event loop through asyncio.to_thread because they run subprocesses and one stops to ask a human (src/hardy/claude_runtime.py:127-131). The Ui/BlockingUi pair (src/hardy/tui/ports.py) exists exactly to marshal that prompt back onto the loop — the async-only Ui docstring notes that blocking the loop while waiting for keys "deadlocks by construction" (src/hardy/tui/ports.py:50-56).

CAS kernel

One long-lived subprocess behind one stdin stream, with three bindings able to reach it (chat, staged runs, MCP). Everything is serialised under self._lock, and reader threads drain stdout/stderr into buffers (src/hardy/cas.py:564-596). The file's header states the serialisation rule as something enforced here rather than by callers.

Process-global mutation of a third-party library, at import time. src/hardy/tui/shell.py:85-92 writes two entries into prompt_toolkit's module-level ANSI_SEQUENCES dict and then clears its private prefix-ambiguity cache. The comment argues correctly that this is idempotent and runs once per process. It is still a library's global state being edited by an application, and it happens as a side effect of importing a module.

Risk ranking

1. No sandbox, by design, on every execution path. Generated Lean, generated TeX, and CAS cells all run as ordinary subprocesses with the user's privileges; a cell can call os.system, Macaulay2's run, or Singular's system("sh", …). This is acknowledged in DESIGN.md, AGENTS.md and src/hardy/cas.py:21-23 — the mitigation is disclosure, and disclosure is not confinement. Blast radius: the developer's machine. It is first on this list not because it is unknown but because it is the only item whose worst case is unbounded.

And the disclosure has a hole. DESIGN.md says the warning is stated on every surface that can execute a CAS cell, which is true: chat banner, the staged run's typed acknowledgement, the MCP tool descriptions, every exported script header. But hardy batch executes generated Lean with no pre-execution disclosure at all — _batch goes straight into run(...) (src/hardy/cli.py:199-204) with nothing resembling ProveWorkflow's acknowledge_unsafe_execution() gate (src/hardy/workflow.py:159), and the batch runner's warning string is attached only to the returned result and the writeup (src/hardy/runner.py:17, :117, :120) — after Lean has already run. It is the legacy smoke path and its blast radius is the same as any other; either it gains the gate or the project's "every surface" phrasing needs the qualifier.

2. Half the codebase is tests and none of it is measured. 10,977 LOC across 68 test files, no pytest-cov, no coverage artifact, nothing in CI producing one. The invariants above are the whole value of the project, and there is no evidence about which of them a test would actually catch breaking. Adding coverage measurement is the single cheapest risk reduction available here.
3. Five private prompt_toolkit internals patched, pinned only below the next minor. ANSI_SEQUENCES, _IS_PREFIX_OF_LONGER_MATCH_CACHE, Application._on_resize, Application._running_in_terminal, and Window.render_info (src/hardy/tui/shell.py:39-40, :85-92, :287, :751-757). The resize patch even cites line numbers inside prompt_toolkit's own source, which will drift on any upgrade. The <3.1 cap in pyproject.toml is doing real load-bearing work. What breaks depends on which internal moves, and the two cases are not equally survivable. A reshaped method — _on_resize, _running_in_terminal, render_info — fails once the shell is constructed, inside the try at src/hardy/tui/__init__.py:35-42, so the plain-UI fallback catches it and masks it as a mysterious downgrade. If either name is renamed or removed, the ImportError escapes run_session entirely and hardy chat does not start at all. So the fallback covers three of the five patches and not the other two; moving that import inside the try would make the guarantee match the claim.
4. The interactive axiom gate is bypassed by a Lean modifier. private axiom Sneaky : False does not match the line-anchored detector at src/hardy/chat.py:335-336, so it is saved with no approval prompt, and the interactive path runs no #print axioms to catch it afterwards. Anything proved from it is then a theorem standing on False with nothing in the workspace recording that. This is the one item here that is a live correctness hole rather than a documentation or design concern, and the fix is small: match Lean's declaration modifiers, or run the audit on save.
5. Two divergent implementations of the hole/axiom gate. The interactive surface's check is weaker than the verifier's in ways that are partly deliberate and partly accidental (opaque permitted, comments not stripped, no axiom audit), and nothing marks which is which. Consolidating into one parameterised gate would turn an emergent difference into a declared one — and would have caught the modifier gap above.

Overloaded words

accept means four different things.
  • hardy accept — the CLI command that runs the checked-in benchmark set (src/hardy/cli.py:624), backed by src/hardy/acceptance.py.
  • CellRecord.accepted — a CAS cell that succeeded and is safe to replay, so it joins the set rebuilds and exports are built from (src/hardy/cas.py:1284).
  • Lean "accepting" a source — kernel acceptance, the only thing that justifies verified (src/hardy/verifier.py:155).
  • acknowledge_unsafe_execution — the human accepting the no-sandbox warning (src/hardy/workflow.py:78). Correctly named acknowledge, which is why it is the least confusing of the four.

The collision that could actually mislead is the second and third: a CAS cell being "accepted" carries no verification weight whatsoever — DESIGN.md is emphatic that "nothing computed here is evidence" — while Lean accepting a proof is the entire point. Same verb, opposite epistemic status.

stage / staged names two unrelated mechanisms. src/hardy/staged.py is the staged run — the phased prove pipeline's model runtime (ClaudeStagedRuntime, and StagedThread at src/hardy/staged.py:97). LeanWorkspace.stage() (src/hardy/workspace.py:455) is staging in the git sense: a shadow copy that is built before being committed. A reader who has met one meaning will misread the other; "shadow" is already used in the code for the second concept (src/hardy/chat.py:455-457) and would be the better public name.
official_checks is undefined in the docs and meters two different things. The name appears in no document — not DESIGN.md, not FEATURES.md — yet it is a frozen run budget (src/hardy/domain.py:31, default 40). It bounds the proof-attempt loop in src/hardy/workflow.py:312, and separately serves as a decrementing quota on check_proof tool calls in src/hardy/mcp_server.py:47-58. In a staged run both meters are live at once against the same number. Nothing explains what makes a check "official" as opposed to the informal Lean checks a model makes while exploring — which appears to be the intended distinction, and is exactly the sort of thing a name should not leave to inference. (src/hardy/acceptance.py:192 overrides it to 1, which reads clearly only once you know it means "one attempt".)
verify is almost reserved for the Lean authority — and the exception is in the CAS layer. The check/verify split is deliberate and mostly held: "check" is provisional (check_proof, _check_lean, _check_latex, hardy doctor's checks) while "verify" marks the independent final authority (FinalVerifier.verify, VerificationResult, verification_sha256). DESIGN.md:32 states the rule out loud: "TeX compilation checks document construction, not mathematical truth."

But CAS export uses the same word for a different and much weaker claim. Verdict includes "verified" (src/hardy/cas_export.py:55), CellVerdict records it, ExportReport.verified counts it, and script_verdict can be "verified" too (src/hardy/cas_export.py:64-78). There it means this cell reproduced its recorded output — reproducibility, not formal truth — in a subsystem whose own module docstring insists nothing it computes is evidence. That is the one place the vocabulary undercuts the epistemic distinction it otherwise protects: a reader skimming an export report for the word "verified" finds it, and it does not mean what it means everywhere else in Hardy. Renaming the CAS verdict to reproduced would cost one enum and close the gap — and would match the property already named ExportReport.reproduces (src/hardy/cas_export.py:81-87).
