hardy — kernel-verification-evidence — Review

Derive the kernel-verified hash from its evidence instead of trusting the field

base main @ 3917807 → claude/kernel-verification-evidence-wa4764 · +668/−83 · generated 2026-07-30

A kernel_verified grade can no longer be written by populating a field.

Before this change, Grades.verification_sha256 was a free-form string that only had to be non-empty, and nothing ever recomputed it. The grade said "kernel verified" because a field was set, not because anything tied that field to the run's evidence. This change makes the number a derived value: Grades now carries the record the digest is taken over (claim hash, Lean source hash, reported axioms, toolchain) and recomputes the digest from it, at construction and on every read-back.

The same record is embedded in lean/verification.json, which validates its own digest, and validate_run_consistency rebuilds the record from the run directory instead of comparing two copies of a self-reported hash. The persisted manifest schema changed shape, so RunManifest.schema_version moved from 1 to 2.

What the change deliberately does not establish is that Lean ran. The axiom list is the one component of the evidence with no second witness on disk.

The fixture can still assert a kernel it never ran. The issue called _DeterministicVerifier "the sharpest illustration" of a structural gap. The structural half is closed — the digest is derived, and the fixture's evidence must name the real claim and the real source bytes. The remaining half is not closed and cannot be closed by hashing: evidence.axioms has no second witness in the run directory, so an injected verifier can still declare an empty axiom set for a proof Lean never elaborated. The change states this limit in four places rather than papering over it (DESIGN.md:29-34, FEATURES.md:61-66, ARCHITECTURE.html:51, and the atlas Invariants tab). Closing it needs an unforgeable attestation or re-elaboration at audit time — a separate change.

Undisclosed by the issue, introduced by the fix: a persisted-format break. RunManifest is extra="forbid", so adding grades.verification_evidence means a manifest written by this build cannot be read by any earlier one, and a version-1 manifest graded kernel_verified cannot be read by this one. schema_version moves 1 → 2 to say so (src/hardy/domain.py:214-221). No migration is provided and none is offered. The practical blast radius is nil today — the only reader of a persisted manifest is validate_run_consistency, called on a run the same process just produced (src/hardy/cli.py:544, src/hardy/cli.py:577) — but any run directory on someone's disk from before this commit is now unreadable, and that is a reviewer's call to accept, not the author's to assume.

Findings

1 · Persisted-format break, announced but not migrated. schema_version moves 1 → 2 (src/hardy/domain.py:214-221). Because RunManifest is extra="forbid", this is the honest choice — a v1 reader would reject a v2 document regardless — but it means every run directory written before this commit is unreadable, including ones whose grades this change would not otherwise invalidate. Today only validate_run_consistency reads a persisted manifest, and only for a run the same process just produced (src/hardy/cli.py:544, src/hardy/cli.py:577), so nothing in-tree breaks. Accept it as a deliberate break of a pre-1.0 format, or ask for a v1 reader — but do not let it pass unnoticed.

2 · A branch that cannot be reached, kept on purpose. src/hardy/acceptance.py:323-328 reports "verified grade carries no verification evidence" for a state Grades's own validator makes impossible — a RunManifest that validated cannot hold a kernel_verified grade without a record. The comment says so. The defence is that this function's contract is to report rather than trust, and the alternative is an AttributeError out of an audit. The objection is that it is dead code, untestable, and will read as a live check to the next person. A reviewer may reasonably ask for it to be removed and the narrowing done differently.

3 · The axiom list is still an unwitnessed assertion. Of the four evidence components, three are checkable against the run directory; axioms is not. The audit checks it against ALLOWED_AXIOMS (src/hardy/acceptance.py:334-336) and checks the saved source ends with the #print axioms line whose output it claims to record (src/hardy/acceptance.py:363-364), which is as far as hashing reaches. It is not a proof that Lean ran. The change says this in DESIGN.md:29-34 and in _verified_run_issues's docstring rather than implying otherwise, which is the right call — but a reader who stops at "kernel_verified is now linked to its evidence" will overread it.

4 · The new source check hard-codes a fixture's shape into the audit. Requiring lean/Main.lean to end with the axiom-report line (src/hardy/acceptance.py:363) is true of everything verification_source produces today, and the format is shared through axiom_report_line so the two cannot drift silently (src/hardy/verifier.py:221-228). Still, it is a positional assertion about a generated file: a verifier that appended one more directive would fail an audit for a reason that is not a defect. Low severity, worth knowing.

Adversarial pass

Attacks run against the change, each with the concrete state it needs. Two produced a defect; three were attempted and refuted, which is recorded because a silent gap reads as a clean bill of health.

Found and fixed · the manifest's own toolchain was unchecked. The change cross-checks evidence.toolchain against the frozen claim, but RunManifest.environment — the field a reader quotes to reproduce a result — was covered by no hash and compared to nothing. Failing case: take a clean verified run directory, edit manifest.json so environment.mathlib_revision names a different revision, load it with RunManifest.model_validate_json and audit it — zero issues reported, and the manifest advertises a toolchain that never ran. That is the reported bug's exact shape, one field over. Closed by a comparison against the claim's environment, which is inside the claim hash (src/hardy/acceptance.py:391-395), pinned by tests/integration/test_manifest_consistency.py:194-216, which fails without it.

Open nit · corrupt artifacts are handled two different ways. _verification_record_issues turns a ValidationError into an audit finding (src/hardy/acceptance.py:290-293), but formalization.json, manifest.json and trajectory.jsonl are still parsed unguarded in the same function. Failing case: truncate formalization.json in a run directory — validate_run_consistency raises out of the audit instead of reporting, while the identical corruption in verification.json is reported. Pre-existing for the other three; this change makes the inconsistency visible rather than causing it. Not fixed here — widening it is a separate pass over the whole function.

Open nit · the digest is now a load-time input, forever. Before, verification_sha256 was inert on read-back. Now Grades will not deserialize unless VerificationEvidence.digest recomputes to the stored value, which pins json.dumps(model_dump(mode="json"), sort_keys=True, separators=(",", ":")) as a permanent wire format. Failing case: a pydantic release that changes json-mode dumping of tuple[str, ...] or of a nested model makes every previously written verified manifest unreadable. The record holds only strings and tuples of strings, so the probability is low — but this coupling did not exist before and nothing in the repo pins it.

Attacked and refuted

  • model_copy bypasses the validator. True — grades.model_copy(update={"verification_sha256": "x" * 64}) really does produce an invalid Grades, and src/hardy/workflow.py:387 uses model_copy. Refuted as a hole: RunManifest(grades=forged) re-validates the nested model and raises, and RunStore.finalize only ever writes a RunManifest (src/hardy/storage.py:120-121). Verified by running it.
  • The audit is silent on an under-claim — a run graded partial whose verification.json says verified. Refuted: the verifier writes lean/Main.lean before lean/verification.json (src/hardy/verifier.py:216-217), so reaching that state needs Main.lean deleted, which trips both "non-verified run unexpectedly has lean/Main.lean" and the artifact-hash check.
  • Secret leakage through the trajectory. _finalize now writes the evidence record into the terminal event, and storage._redact only matches a fixed key list. Refuted: every field is a hash, a version string, or an axiom name — no credential-shaped key or value is introduced.
